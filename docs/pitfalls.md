<a id="r-01"></a>
## R-01: UniDic のライセンスと再配布

UniDic CWJ 3.1.1 は **GPL / LGPL / BSD 3-Clause のトリプルライセンス**で、利用者が選べる。
BSD 3-Clause を選べば、MIT / Apache 2.0 のソフトウェアへの同梱・商用利用・再配布ができる。
条件は、著作権表示・条件一覧・無保証条項を保持することと、UniDic Consortium の名前を派生物の推奨・宣伝に使わないこと。

このリポジトリには辞書を含めていない（サイズの都合。`lex_3_1.csv` だけで 233 MB）。
辞書や、辞書から作ったキャッシュ・モデルを配布するときは、上の条件を満たすこと。

<a id="r-02"></a>
## R-02: Oracle が 100% にならない

Oracle（辞書ラティスに正解読みがあるか）は、**スコープ内 99.90% / 全体 99.46%**。
全体の失敗 73 件のうち 60 件は数字・ラテン文字を含む文（[R-05](#r-05)）。論文は 100.00% を報告している。

Oracle が低いときは、この順で疑う: (1) `pron` だけ / `kana` だけを使っていないか（片方だけでは 31〜34% に落ちる）、
(2) カナ正規化が benchmark と一致しているか、(3) 未知語フォールバックの漏れ、(4) 辞書のカバレッジ。
**95% を下回るならバグを疑う。**

<a id="r-03"></a>
## R-03: 論文を完全には再現できない

論文の公式コード・学習コード・合成データ・プロンプトはいずれも公開されていない。
99.62% に届かなかったとき、実装の誤りかデータの差かを判別できないので、**論文値の再現を目標にしない**。
判断基準は「同じ評価コードで自前で走らせた既存手法（OpenJTalk / MeCab）との差」に置いた。

<a id="r-04"></a>
## R-04: 固有名詞

論文は学習データから固有名詞を除いている。このリポジトリも固有名詞は改善の対象外だが、Hard Set で測った。
**「辞書に無いから解けない」は当たらなかった。** 語レベルの Oracle は 97.3%（UniDic は人名・地名を持つ）で、
難しさは辞書にある複数候補からの選択にある。人名はどの UniDic 系の構成も OpenJTalk を上回った（87〜95% vs 76.9%）。

<a id="r-05"></a>
## R-05: 数字・英字・単位

`2026年`・`RTX 5090`・`100km/h` のような表記は、**前段のテキスト正規化（Text Normalizer）が扱う前提**で、範囲外とした。
benchmark 13,536 文のうち 87 文（0.6%）が数字・ラテン文字を含む。`24時間 → ニジュウヨジカン` のように、
読みは G2P ではなく正規化の問題である。

- 評価スクリプトは「スコープ内 / 全体」の 2 系統で報告する
- 学習データ生成では算用数字・英字を禁止している
- 漢数字 + 助数詞（`三本`・`六階`）は範囲内で、専用のデータを作った（→ [training.md](training.md#4-数詞--助数詞)）

<a id="r-06"></a>
## R-06: CPU レイテンシ

目標は 50 字・batch 1・CPU で 20 ms 未満。**91 字 p50 2.59 ms**（size-xs 2.07M・INT8・1 スレッド）で達成した。
ただし OpenJTalk（0.17 ms）より 1 桁遅い。

初回計測は 91 字で **57 ms** だった。設計に書いてあった「読み表現のキャッシュ」を実装し忘れていた（入れて 9.1 倍速）。
**設計に書いた最適化を実装したか、測る前に確認すること。**

<a id="r-07"></a>
## R-07: ストリーミング非対応

文全体を文脈エンコーダに入れるので、文末まで待たないと処理を始められない。非ストリーミング用途に限定している。

<a id="r-08"></a>
## R-08: 文字単位の事前学習モデル

論文は文字単位の日本語 DeBERTa を使う。文字単位の小型モデルは実在した
（`ku-nlp/deberta-v2-tiny-japanese-char-wwm` 5.77M など）が、**CC BY-SA 4.0（コピーレフト）**なので、
寛容なライセンスで配布する経路には使わず、スクラッチの文字単位 Transformer を採用した。
事前学習モデルは精度の上限を測る参照としてだけ残した（`configs/tiny-pretrained.yaml`・`hf` extra）。
辞書事前分布を入れると、事前学習の利得は +4.77 → +0.52 pt（判定不能）まで縮んだ。
サブワード単位のモデルは、文字位置とラティスの位置が 1 対 1 に対応しないので使わない。

<a id="r-09"></a>
## R-09: 生成データの品質・多様性

LLM 生成データは文体・話題が偏りやすく、**生成モデルで品質が大きく違う**。
助詞「は→ワ」の規則違反率は opus 0.5% / haiku 30.6%（起動時に最重要ルールを再掲して 4.4%）。

- 4 段フィルタ（形式・ラティス整合・対象語一致・重複）と、助詞の読みチェック・同語への矛盾ラベル検出
- dev は**語（`target_surface`）単位で**学習データから分離する。文単位で分けると同じ語が両側に出る
- フィルタで検出できない文脈的な誤読（`その村 → ソン`）は残る。dev の監査（[R-19](#r-19)）で拾う

<a id="r-10"></a>
## R-10: カナ正規化の二重定義

辞書・データ生成・評価でカナ正規化が別実装になると、Oracle が落ちた原因が正規化なのか辞書なのか判別できず、
数値が他手法と比較できなくなる。**`src/lattice_g2p/kana.py` の単一実装をすべてが通す**（[architecture.md](architecture.md#9-設計上の不変条件) 不変条件 2）。

<a id="r-11"></a>
## R-11: ベンチマークへの過適合

常用漢字の benchmark だけを見ると、固有名詞や数詞で崩れるモデルを高く評価してしまう。

- ハイパーパラメータは dev で選び、benchmark では選ばない
- 弱点領域はカテゴリ別の Hard Set で測る
- 誤りは 3 分類（Oracle 失敗 / 経路選択の誤り / 正規化の不一致）で出す

<a id="r-12"></a>
## R-12: ノードスコアリングのバッチ化漏れ

`for node in nodes: model(node)` は動くが、1 文で数百 ms〜1 秒を超える。**動くので気づきにくい。**
`NodeScorer.score(text, nodes)` はノード全体を一度に受け取り、**単体のノードを受けるメソッドを作らない**。
この対策として入れた「バッチ計算と単体計算の一致」テストが、別のバグ（[R-18](#r-18)）を見つけた。

<a id="r-13"></a>
## R-13: クラウドで CPU レイテンシを測る

クラウド GPU のインスタンス（vast.ai など）は CPU を他テナントと共有し、型番も vCPU 割り当ても一定しない。
**そこで測った CPU レイテンシには再現性が無い。** しかも数値は「それらしく」出るので気づきにくい。

```
✓ クラウドで学習 → checkpoint を回収 → ローカルで ONNX 化 → ローカル CPU で計測
✗ クラウドのインスタンス上で CPU レイテンシを測る
```

計測結果には CPU 型番・スレッド数・メモリを記録する。

<a id="r-14"></a>
## R-14: クラウド GPU の中断・課金

インスタンスは予告なく止まることがあり、破棄し忘れると課金され続ける。

- checkpoint を定期保存し、optimizer と乱数の状態ごと再開できるようにする（`scripts/train.py` は `latest.pt` から自動で再開する）
- 学習が終わったら**自分が起動したインスタンスだけを**破棄する（`infra/vast_teardown.sh`）

<a id="r-15"></a>
## R-15: 評価指標の定義ミスがモデルの欠陥に見える

対象語の読みを「経路上で対象語と重なるノードの読み」として取り出したら、Accuracy が **11.15%** にしかならなかった。
「固める → カタメル」のように、経路が対象語（「固」）をまたぐ 1 ノードを選ぶためである。モデルの読みは正しかった。

同じ構造のバグを 2 回踏んだ（学習中の評価でも「損失 0 なのに Accuracy 80.5%」）。

- 対象語は、**予測した文全体の読みの、正解が示すカナ位置**で見る（11% → 65%）
- 精度は**文全体の読みの一致**で測る。分割に依存する指標は「形態素分割を正解にしない」という前提と矛盾する
- 精度が想定外に低いときは、モデルを疑う前に誤り例を目視する

<a id="r-16"></a>
## R-16: データ選定が学習価値の高い語を落とす

多音語の抽出結果に `米`・`生`・`人`・`日` が 1 語も入っていなかった。「29,241 語を抽出」という件数は妥当に見えた。

- 固有名詞の読みを 1 つでも持つ表記を丸ごと除外していた → 対象の品詞だけを見る
- 読み数の上限で除外していた（`生` は 46 読み）→ コストの小さい順に上位 N 個を採る
- 長音の書き分け（`コウ / コー`）を同一視していなかった → `phonetic_key` で畳む（153,422 → 29,241 語）

**件数や分布では中身の妥当性は分からない。上位 30 件を目視する。**

<a id="r-17"></a>
## R-17: 学習データ量が桁違いに少ない

論文は 234 万文、このリポジトリは生成 6,554 文（0.3%）。当初は精度不足の主因と考えたが、
**データ 4 倍・語彙 8 倍でも対象語は +0.95 pt しか動かなかった。**
OpenJTalk との差の正体は、連接行列と、辞書の重複排除で失っていた品詞だった（[R-27](#r-27)・[results.md](results.md)）。

<a id="r-18"></a>
## R-18: 空読みノードが attention を nan にする

句読点の読みは空文字で、読みをエンコードすると**全位置がマスクされた行**になる。
その行は attention の softmax が `nan` を返し、行列積を通じて**バッチ全体が nan になる**。
日本語の文はほぼ必ず句読点を含むので、全サンプルが汚染される。

- 空読みに専用 ID（`EMPTY_READING_ID`）を割り当て、0 ベクトルにしない
- 全マスク行は `safe_mask` で先頭を有効にして計算し、出力側で元のマスクを掛ける

「等価な 2 経路を比べる」テスト（バッチと単体）で見つかった。期待値を書き下すテストでは書けなかった。

<a id="r-19"></a>
## R-19: dev のラベル品質が精度の天井を作る

データを 4 倍にしても dev の精度が動かなかった。上位のモデルで dev の誤りを監査すると、
**誤り 130 件のうち 43 件（33%）が評価側の問題**だった（対象語 68.97% → 75.89%）。

```
法師 → ボウシ（誤り。ホウシ）     大麻 → オオヌサ / タイマ（どちらも成立）
```

- **評価セットも実装物である。** モデルと同じように疑う
- 安いモデルで作ったラベルを同じモデルで監査すると、同じ誤りを同じように見逃す。**監査は 1 段上のモデルで**
- 両方成立する読みは「複数正解」の対応表（`data/dev_audit_r21.jsonl`）に入れ、評価で受け入れる

<a id="r-20"></a>
## R-20: 1 文字の対象語は語単位で分離できない

生成データは文全体の読みが教師なので、dev の語（`方`・`後`・`山` など）が学習文の本文に出るだけで読みを教えてしまう。
1 文字の常用漢字は日本語の文からほぼ排除できないので、**受容した**。
実測では、本文に出る語の方が完全に未知の語より精度が低く（69.81% vs 82.13%）、dev を過大評価してはいなかった。

ルビ由来のデータは span の外にラベルが付かないので、ルビが付いた span を落とすだけでよい（`drop_held_out_spans`）。

<a id="r-21"></a>
## R-21: 推論できない語を held-out にする

数詞 `四`・`六`・`八` を dev に取り分けたまま、ほかの数詞で音便を教えようとした。
学習データで促音化する数詞は `一`・`十` の 2 つ、しないものは 5 つで、`六本 → ロクホン` は与えたデータから導ける唯一の結論だった。
**促音化するかは規則ではなく語彙的知識である。** データを足しても事前学習を入れても、誤りは 34 件から動かなかった。

**held-out にしてよいのは「推論できるもの」だけ。** 数詞は学習データに入れ、dev から外した
（`split_train_dev.py --dev-exclude-chars`）。

<a id="r-22"></a>
## R-22: 比較相手の出力形式を検証しない

2 回起きた。どちらも「相手が弱い」という数字になった。

| 相手 | 誤り | 影響 |
|---|---|---|
| OpenJTalk | `pron` のアクセント記号（`マイツ’キ`）を落とし損ねた | 対象語 96.85% → 93.50% と過小評価し「並んだ」と誤報告 |
| MeCab + UniDic | 助詞を pron 形で組み立て `を → オ` にした（benchmark は `ヲ`） | 文一致 85.27% → 42.82% と過小評価 |

- 比較相手の出力に想定外の文字が残っていないかを機械的に確かめる（`baselines.find_unexpected_chars`。`compare_systems.py` は残ると止まる）
- **「相手が弱い」という数字が出たときこそ、自分の組み立てを疑う**

<a id="r-23"></a>
## R-23: 指定した読みにならない文が生成される

「米をコメと読む文」を頼んでも、文脈上ベイと読む文が返ることがある。
ラティス整合フィルタは「その読みで生成できるか」しか見ないので、文脈として自然かは検出できない。
dev の監査（[R-19](#r-19)）で拾う。

<a id="r-24"></a>
## R-24: 1 回の実行では 0.6 pt 未満の差を判定できない

同じ条件で学習し直すと、benchmark の対象語が**約 0.30 pt ずれる**（seed 3 本なら SD 0.11 pt）。
それ以前に 1 回の実行で報告した小さな差（+0.36 pt など）は、反復するとすべて判定不能になった。

| 差 | 扱い |
|---|---|
| 2 pt 以上 | 報告してよい |
| 0.6〜2 pt | 2 条件 × seed 3 本で反復する |
| 0.6 pt 未満 | **反復せずに報告しない**（「差は無い」とも言えない） |

- `scripts/train.py --seed 42`（1337 / 2024 でも回す）
- 学習しない比較（同じ checkpoint に連接行列を足す・評価の数え方を変える）は決定的なので、反復は要らない
- 構成によってばらつき自体が変わる（CRF の遷移項を入れると SD が 4 倍になった）

<a id="r-25"></a>
## R-25: `Entry` に足したフィールドが黙って落ちる

辞書キャッシュは `Entry` をタプル化して保存し、`from_entries` は `Entry` を作り直す。
フィールドを足して `_CACHE_FIELDS` と `from_entries` を直し忘れると、**例外も警告も出ずに既定値になる**
（連接 ID が全件 0 になった）。回帰テストは `dataclasses.fields` で全フィールドを往復比較している。

<a id="r-26"></a>
## R-26: INT8 の読みキャッシュが評価の履歴に依存する

同じ INT8 モデル・同じ 300 件で、対象語が 94.33% と 94.67% に分かれた。違いは直前に流した文だけだった。

**原因:** 動的量子化は活性の尺度をバッチ全体の min / max で決める。読みエンコーダは「その文で初めて出た読み」を
1 バッチで計算してキャッシュするので、**同じ読みでも、最初に一緒に計算された読みでベクトルが変わる。**
TTS では、同じ文の読みが直前に処理した文で変わりうる。

**対処:** `export_onnx.quantize()` は読みエンコーダを FP32 のまま写す（`KEEP_FP32`）。
読みはキャッシュされるので速度はほぼ変わらない（size-xs 2.86 → 4.15 MB）。
「同じ入力なら同じ出力」をテストで縛っている（`tests/test_export_quantize.py`）。

**キャッシュと、バッチに依存する計算（動的量子化・バッチ正規化など）を組み合わせると、出力が履歴に依存する。**

<a id="r-27"></a>
## R-27: (表記, 読み) の重複排除が連接の情報を壊す

既定の辞書は (表記, 読み) で 1 つに潰し、**最小コストのエントリの品詞と連接 ID だけを残す**。
連接行列は品詞（文脈 ID）で引くので、潰すと連接の情報が壊れる。

```
実施される → 「実 / 施さ(ホドコサ) / れる」   さ が終助詞の 1 ノードしか残らず、サ変の未然形が消える
```

辞書 + 連接行列は実 MeCab より対象語で 1.18 pt 低かった。
**`Dictionary.from_entries(..., keep_pos=True)`**（`build_dict_cache.py --keep-pos`）で品詞違いを別に残すと、
辞書 + 連接行列が実 MeCab を 1 件単位でほぼ再現した（対象語の正誤が 13,536 件中 13,528 件で一致）。
ラティスのノードは約 2 倍になる。既定の辞書とラティスは変えていない。

**連接行列を使うなら、品詞を保つ辞書を使う。** 近似を比較の基準にするなら、本物も 1 度は測ること。

## R-28: 自前の数え方が公式評価ツールと違う

論文の数値は、benchmark の公式評価ツール（`jkyb-eval`）の値である。保存済みの予測を公式ツールに通すと、
自前で走らせた OpenJTalk が論文と 3 列とも一致した（96.63 / 3.00 / 0.80）。

自前の「対象語」は「対象語にかかるノードの読みに、正解が部分文字列として含まれるか」で数えていて、
**公式より 0.2〜0.6 pt 甘く、甘さは構成によって違った**（ノードが長いほど甘い）。
同じ物差しどうしの差と結論は変わらなかったが、軽量構成と OpenJTalk の差は 2.55 pt ではなく 2.93 pt だった。

**対処:** `compare_systems.py` と `run_m7.py` は既定で公式ツールの値も出す（`lattice_g2p.official_eval`。版を固定）。
**論文や他の報告と比べるときは公式ツールの値を使う。** 公式の評価コードがあるなら、自前の実装より先にそれを使う。
