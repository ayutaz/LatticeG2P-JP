## 1. 評価指標

### 1-1. Accuracy（対象語）

**対象語（benchmark の各文に 1 つある、評価対象の漢字語）の読みが、許容される読みのいずれかと一致した文の割合。**

対象語の予測読みは、**予測した文全体の読みの、正解が示すカナ位置**で見る。
経路上のノードから取り出してはいけない。経路が対象語をまたぐ 1 ノード（「固める → カタメル」で対象語は「固」）を
選ぶことがあり、ノードから取り出すと正しい読みが不正解になる（[R-15](pitfalls.md#r-15)。これで Accuracy が 11% → 65% と変わった）。

正解読み（`readings.natural`）は複数ありうる（13,536 文中 75 文。`憧憬 → ショウケイ / ドウケイ`）。
いずれかに一致すれば正解とする（`metrics.accuracy_any`）。`readings.marginal`（辞書上は許容できるが文脈では一般的でない読み）は含めない。

### 1-2. Target PER

対象語の読みに対する編集距離ベースの誤り率。論文は PER（Phoneme Error Rate）と呼ぶが、実態はカナ列に対する CER である。

### 1-3. Sentence PER と文一致

文全体のカナ列に対する編集距離ベースの誤り率と、文全体の読みが完全に一致した割合（文一致）。
**精度は文全体の読みで測るのが原則**で、対象語の一致は参考値である（[R-15](pitfalls.md#r-15)）。
文一致と対象語の両方を見ること。対象語が正しくても、別の語（「会う → オウ」など）で文一致を落とす。

### 1-4. Oracle

**辞書ラティスの中に正解読みがあるか**だけを測る。スコアラは使わない。

```
Oracle = (正解経路集合 G が空でない文数) / 全文数
```

実装は CRF の分子と同じ制約付き forward（[architecture.md](architecture.md#5-7-oracle--g-が空でないか)）で、到達可能性だけを見る。
**学習データのラティス整合フィルタと同じ処理**である。

| Oracle | 意味 | 次の手 |
|---|---|---|
| ≥ 99.5% | 手法の前提が成立 | 経路選択の改善へ |
| 95〜99.5% | 辞書のカバレッジが不足 | 落ちた例を分類して辞書を補う |
| < 95% | **正規化かフィールド選択のバグを疑う** | `pron` と `kana` を両方使っているか、正規化が一致しているか |

実測: スコープ内 **99.90%** / 全体 99.46%（全体の失敗の 82% は数字・ラテン文字を含む文。[R-05](pitfalls.md#r-05)）。

### 1-5. 公式評価ツール（jkyb-eval）との関係

**論文の数値は benchmark の公式評価ツール `jkyb-eval` の値である。** 自前で走らせた OpenJTalk の予測を公式ツールに通すと、
論文と 3 列とも小数第 2 位まで一致した（96.63 / 3.00 / 0.80）。

| 論文の列 | 公式ツールの指標 |
|---|---|
| Accuracy | `accuracy`（自然な読みとの完全一致） |
| Target PER | `relaxed_target_kana_cer` の `cer_at_1`（文ごとに上限 1.0 で平均） |
| Sentence PER | `sentence_kana_cer` の `cer_at_1` |

| | 公式 | このリポジトリの自前の数え方 |
|---|---|---|
| 対象語の取り出し | 文全体の読みの中で、前後の文字列との編集距離で位置合わせ | 対象語にかかるノードの読みに、正解が部分文字列として含まれるか |
| 正規化 | NFKC・記号除去・長音 → 母音・オ段 + ウ → オ・エ段 + イ → エ・ヂヅヲヰヱ → ジズオイエ | `phonetic_key`（長音・四つ仮名） |
| 文の誤り率 | 文ごとの CER（上限 1.0）の平均 | コーパス全体の CER |

★**自前の数え方は 0.2〜0.6 pt 甘く、甘さは構成で違う**（ノードが長いほど甘い）。
同じ物差しどうしの差と結論は変わらなかったが、**論文や他の報告と比べるときは公式の値を使う**（[R-28](pitfalls.md#r-28)）。

`scripts/compare_systems.py` と `scripts/run_m7.py` は、自前の値に加えて**既定で公式ツールの値も出す**（`--no-official` で止める）。
中身は `lattice_g2p.official_eval` で、予測を公式の形式（`{"key": ..., "yomi": 文全体の読み}` の JSONL）で書き出し、
版を固定した公式ツールを `uv run --no-project --with` の一時環境で動かす
（公式ツールは `huggingface-hub<1` を要求し、このプロジェクトの依存と衝突するため）。初回はネットワークが要る。
部分集合（`--limit`）で測るときは、その文だけのデータセットを渡すので同じ規則で測れる。

## 2. カナ正規化

**辞書・学習データ生成・評価のすべてで同じ関数を通す**（`src/lattice_g2p/kana.py` の `normalize_kana()`。[R-10](pitfalls.md#r-10)）。
規則は benchmark 13,536 文の実データを集計して決めた（`scripts/inspect_charset.py`）。

| 項目 | 規則 | 根拠（benchmark の集計） |
|---|---|---|
| 文字種 | NFKC で全角カタカナに統一、ひらがな → カタカナ | — |
| 長音 | **表記どおり（ウ を残す）。既存の「ー」は保持** | 「ー」1,064 回はすべて外来語。漢字語の長音は「ウ」 |
| 助詞「は」「へ」 | **ワ / エ**。ただし正規化では変換せず、辞書の `pron` に任せる | ワ 11,614 回・エ 2,716 回 |
| 助詞「を」 | **ヲ のまま** | ヲ 7,498 回 |
| ヂ / ヅ | 変換しない | ヅ が 49 回そのまま出現 |
| 句読点・括弧・感嘆符・空白 | すべて除去 | カタカナ以外は 8 種のみ（。、？「」！『』） |
| 小書き文字・ヴ | 保持 | `ァ ィ ェ ォ ッ ャ ュ ョ` が出現 |

- **助詞の読みを正規化で文脈判断しない。** UniDic の `pron` が解決している
- **長音符「ー」を除去しない。**「コーヒー」が「コヒ」になる
- 全 13,536 文で、正規化後がカタカナだけになることと冪等性をテストで固定している

### `phonetic_key()`（比較専用）

UniDic の `pron` 形と `kana` 形は、同じ読みを別の表記で持つことがある（`亢 → コウ / コー`・`丙 → ヘイ / ヘー`）。
`phonetic_key()` は長音を表す仮名と長音符を母音に寄せ、**四つ仮名**（チヂム ≡ チジム・ツヅミ ≡ ツズミ）も畳む。

```
コウ → コオ,  コー → コオ     一致
サイ → サイ                   ア段 + イ は長音ではないのでそのまま
```

**出力する読みとしては使わない。** 比較と、多音語の抽出（異表記ペアを多音語と数えない）にだけ使う。
四つ仮名は dev では 0 件だったが、benchmark では 33 件あり、OpenJTalk との差の 5.1% を占めていた。
**母数が 37 倍違えば「0 件」は「1% 未満」としか言っていない。**

## 3. 評価データ

**評価データはどれもリポジトリに含めていない**（`data/` は gitignore）。取得方法は [README](../README.md#データの準備)。

### 3-1. Joyo-Kanji-Yomi Benchmark Parakeet Edition

| 項目 | 内容 |
|---|---|
| 入手元 | Hugging Face `Parakeet-Inc/joyo-kanji-yomi-benchmark-parakeet`（公式評価ツールは GitHub `Parakeet-Inc/Joyo-Kanji-Yomi-Benchmark-Parakeet-Edition`） |
| ライセンス | MIT |
| 文数 | 13,536（1 文に対象語 1 つ） |
| 置き場所 | `data/benchmark/common_kanji_source.jsonl` |

論文が使っている評価セットで、論文値と直接比べられる唯一のデータ。
対象語の位置は数値フィールドではなく `tagged_text` / `tagged_yomi` の `<...>` から導く（ロード時に、タグを除いた文が `text` と一致することを確かめる）。

| `reading_category` | 件数 |
|---|---|
| on_yomi（音読み） | 7,056 |
| kun_yomi（訓読み） | 6,108 |
| joyo_appendix_reading（熟字訓・当て字） | 372 |

★対象語は常用漢字の読みで、**数詞を 1 件も含まない。** 数詞の改善は benchmark では見えない（→ §3-3）。

### 3-2. dev（ハイパーパラメータ用）

学習データと同じ手順で生成した文から、**語（`target_surface`）単位で**分けた 367 文（89 語・数詞を含まない）。
`data/dev_r21.jsonl`。ラベルの監査結果（両方成立する読みの対応表）は `data/dev_audit_r21.jsonl`。

- **ハイパーパラメータは dev で選び、benchmark では選ばない**（[R-11](pitfalls.md#r-11)）。
  例外は `UnigramScorer` の既定値（`node_penalty` など）で、開発初期に benchmark の 2,000 文で決めた。
  ベースラインの配線確認が目的で、ニューラルの調整には dev を使った
- dev の語は、生成データの分割（`split_train_dev.py`）と青空文庫のルビ側の除外（`drop_held_out_spans`）の**両方で**学習から外す
- dev のラベルも疑う。監査で誤りの 33% が評価側だった（[R-19](pitfalls.md#r-19)。監査は生成に使ったより 1 段上のモデルで）
- 推論できない語（促音化する数詞など）を dev に入れない（[R-21](pitfalls.md#r-21)）

### 3-3. Hard Set（弱点領域）

論文が弱点と認める領域を実際に測るための 761 文。**全体の平均だけを見て「よく出た」と判断しないための装置**である。

| カテゴリ | 文 | 例 |
|---|---|---|
| 人名 | 78 | 四月一日（ワタヌキ）・生田目（ナバタメ） |
| 地名 | 168 | 十三（ジュウソウ）・放出（ハナテン） |
| 組織 | 54 | |
| 数詞 + 助数詞 | 168 | 六本（ロッポン）・八分（ハップン） |
| 同表記異読 | 293 | 米を炊く / 米国政府 |

**2 層構造**にしている。

| 層 | 何を測るか | 正解の出どころ |
|---|---|---|
| 語レベル | 辞書にその読みがあるか（Oracle） | **人手で書いた表**（LLM を使わない） |
| 文レベル | 文中で正しく選べるか | 表（対象語）+ サブエージェントが書いた文（文全体。`check()` で機械検証） |

語レベルの Oracle は **97.3%**（UniDic は人名・地名を持つ）。難しさは辞書にある候補からの選択にある。

★**物差しが比較相手に有利に偏っていないかを確かめる。** 作成中に 2 回見つかった
（OpenJTalk が外す語ほど検証で落ちていた / 自由に揺れる読みを片方に固定していた）。

構築は `scripts/build_hard_set.py`（プロンプトは `prompts/subagent-hardset-v1.md`）、評価は `scripts/run_hard_set.py`、
語レベルの Oracle は `scripts/hard_set_oracle.py`。

## 4. 比較対象

同じ評価データ・同じ正規化・同じ評価コードで比べる。

| 手法 | 実行方法 | 備考 |
|---|---|---|
| OpenJTalk | `pyopenjtalk`（`bench` extra） | `pron` のアクセント記号（`’`）を落とす（`baselines.clean_reading`） |
| MeCab + UniDic 3.1.1 | `fugashi` + UniDic の zip の `sys.dic`（`uv run --with fugashi`） | 辞書がこのリポジトリと同じなので最も公平な比較相手。pip の `unidic` パッケージは版が違う可能性があるので使わない |

★**比較相手の出力の組み立ては、2 回とも最初は間違えていた**（[R-22](pitfalls.md#r-22)）。
OpenJTalk はアクセント記号の落とし損ね、MeCab は助詞を pron 形で組み立てて `を → オ` にした。
`find_unexpected_chars` で想定外の文字が残っていないことを確かめ、**「相手が弱い」数字が出たらまず自分の組み立てを疑う。**

MeCab の読みは「助詞は pron 形（は → ワ・へ → エ）、ただし を は kana 形（ヲ）、それ以外は kana 形」で組み立てる。
これは benchmark の表記規則そのもので、精度の調整ではない。

## 5. レイテンシ

### 5-1. 計測条件

| 項目 | 設定 |
|---|---|
| 場所 | ★**ローカルの固定環境**。クラウドのインスタンスでは測らない（[R-13](pitfalls.md#r-13)） |
| batch size | 1 |
| スレッド | 1 |
| 文長 | 約 20 / 50 / 100 字の 3 水準（実際の文は 18 / 47 / 91 字。`scripts/run_benchmark.py`） |
| 試行 | 各 100 回（warm-up を除く） |
| 記録 | CPU 型番・スレッド数・メモリ・OS・Python とライブラリの版 |

★**レイテンシは文長ごとに出す。** benchmark の文は平均 13 字と短く、そこだけ見ると実用の文長での値を誤解する。

### 5-2. 報告する値

- p50 / p95（平均だけを報告しない。TTS では p95 が体感に効く）
- 内訳（lattice / context / scoring / viterbi）
- モデルのサイズ（INT8 / FP32）と辞書のサイズ

`run_benchmark.py` は warm-up（10 回）の後、読みキャッシュが温まった状態を測る。
初めて見る読みばかりの文（キャッシュが冷えた状態）は最悪値で、size-xs の 91 字で p50 23.6 ms だった
（温まった状態は 2.85 ms）。よく使う読みは事前に計算しておける。

```bash
uv run python scripts/run_benchmark.py --model models/size-xs-int8 --threads 1 --openjtalk
```

## 6. 評価するときの注意

### 6-1. 論文値の再現を目標にしない

論文の公式コード・データは公開されていない（[R-03](pitfalls.md#r-03)）。判断は**自前で走らせた既存手法との相対差**で行う。

### 6-2. 学習データ由来の文は評価に使えない場合がある

青空文庫のルビは文の一部にしか読みが無いので、文全体の読みで判定する評価には使えない。
`PreparedExample.gold_reading` が `None` の例は評価の分母から外す（分母に入れると必ず不正解扱いになる）。
**ルビは学習専用。dev と test は生成データと benchmark。**

### 6-3. 誤りを 3 分類する

| 分類 | 意味 | 次の手 |
|---|---|---|
| Oracle 失敗 | 辞書に正解が無い | 辞書の問題。モデルを直しても改善しない |
| 経路選択の誤り | 正解は辞書にある | モデルの問題。**ここが改善対象** |
| 正規化の不一致 | — | バグ |

**この 3 分類を出さない評価は無意味である。** 残りの誤りがどれに属するかで次の手が変わる（`lattice_g2p.analysis`）。

### 6-4. 差を判定する

学習を伴う比較は、同じ条件でも実行ごとに約 0.30 pt ずれる。**0.6 pt 未満の差は seed 3 本で反復するまで報告しない**（[R-24](pitfalls.md#r-24)）。
学習しない比較（同じ checkpoint に連接行列を足す、評価の数え方を変える）は決定的なので反復は要らない。
対応のある比較では「直った件数 / 壊れた件数」と差 / SE を併記する。

### 6-5. 近似を基準にするなら、本物も一度は測る

「UnigramScorer + 連接行列」を MeCab 相当とみなして比べたら、実 MeCab より 1.18 pt 低かった（[R-27](pitfalls.md#r-27)）。
基準にした近似が本物とずれていると、「基準を超えない」の意味が変わる。

### 6-6. dev は外部知識の価値を過小評価しうる

連接行列の重みを dev で選ぶと「行列なしが最良」だったが、benchmark では行列で +1.40 pt だった。
学習データと同じ手順で作った dev は、大規模コーパスから学んだ一般的な知識の効果を見ないことがある。
重みは dev で選ぶ原則を守ったうえで、事前に決めた値と併記する。

## 7. 評価の実行

| やること | コマンド | 必要なもの |
|---|---|---|
| Oracle（辞書のカバレッジ） | `uv run python scripts/run_oracle.py` | 辞書キャッシュ・benchmark |
| ベースライン（UnigramScorer）と誤り分析 | `uv run python scripts/run_eval.py` | 同上 |
| OpenJTalk・UnigramScorer・学習済みモデルを並べる（自前 + 公式の物差し） | `uv run python scripts/compare_systems.py [checkpoints...] --onnx models/<name>` | 同上 + `bench` extra |
| 連接行列を足した構成（辞書 + 行列・ニューラル + 行列） | `uv run python scripts/run_m7.py --runs <run> ...` | 同上 + 学習済みモデル + `matrix.bin` / `unk.def` |
| 実 MeCab + UniDic | `uv run --with fugashi python scripts/run_mecab_reference.py` | UniDic の `sys.dic` など |
| dev で checkpoint を比べる | `uv run python scripts/compare_dev.py checkpoints/<a> checkpoints/<b>` | dev・監査の対応表 |
| Hard Set | `uv run python scripts/run_hard_set.py --onnx models/<name>` | Hard Set |
| レイテンシ | `uv run python scripts/run_benchmark.py --model models/<name> --threads 1` | ONNX モデル |

`run_m7.py` の品詞を保つ構成は `--dict-cache data/dic_cache_pos.pkl` で測る。
